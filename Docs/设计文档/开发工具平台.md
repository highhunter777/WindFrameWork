# 开发工具平台设计

`Assets/WindFrameWork/Editor/Tooling/`，程序集 `WindFrameWork.Editor.Tooling`，命名空间 `WindFrameWork.EditorTooling`。本文仅描述当前最新设计；当前状态为规划中，代码未动工，进度见 [../施工记录/进度.md](../施工记录/进度.md)。

## 目标与边界

编辑态与构建态工具的统一注册、运行与报告：校验与审计、构建与发布、代码生成、编辑器效率四类工具由同一套基建承载，人（菜单 / 工具中心）、Agent（unity-pipeline 命令）、CI（batchmode + 退出码）三个消费方走同一执行入口。

**不做**的事与做什么同等重要：

- 不做运行态工具：机内观测、命令台、作弊入口归调试平台（见 [调试平台.md](调试平台.md)）；
- **零运行时足迹**：纯 Editor 程序集，不进任何 Runtime asmdef——因此不涉激活裁剪、AOT、热更边界，调试平台需要考虑的三道门在此全部不存在；
- 不做线上遥测与发布态数据面；
- 服务端与 Shared 的工具走 .NET 原生生态（dotnet CLI / analyzers），不从客户端移植。

## 时态边界：与调试平台的分工

| | 调试平台 `Modules/Debugging` | 开发工具平台 `Editor/Tooling` |
| --- | --- | --- |
| 时态 | 运行态（机内、开发构建） | 编辑态 / 构建态（编辑器、CI） |
| 载体 | Runtime + Editor 面板 | 纯 Editor 程序集 |
| 约束 | 装配清单裁剪、AOT、热更边界 | 零运行时足迹，无裁剪问题 |

数据监视类窗口（池监视器、模块状态）归其数据源模块的 `Editor/`（调试平台的编辑器侧同样如此）；工具中心只聚合**动作型**工具与校验报告，不吞噬窗口归属。

## 程序集与命名

**命名空间取 `WindFrameWork.EditorTooling` 而非 `WindFrameWork.Editor.Tooling`**：命名空间若含 `…Editor` 段，程序集内裸记号 `Editor` 会解析到命名空间而非 `UnityEditor.Editor` 类型——自定义 Inspector 与 EditorWindow 工具里 `Editor` 是高频基类。与 ObjectPool、UniTaskBridge、Debugging 记录在案的「命名空间与类型同名邻接」陷阱同源。

工具归属规则沿用既有骨架，不新建层级：

- 全仓性工具与基建：`WindFrameWork/Editor/`（按分类开子目录）；
- 模块私有工具：`<模块>/Editor/`，经注册表汇入工具中心；
- 校验某模块资产的规则：实现放该模块 `Editor/`，框架 `Editor/` 只放全仓规则（依赖方向、命名、导入设置）。

## 平台本体：注册表 + 校验运行器 + 工具中心 + 批处理入口

整个基建只有两个契约与一个窗口：

```csharp
// 动作型工具的统一契约：工具中心、菜单、批处理三个入口共用同一注册表
public interface IToolEntry
{
    string Id { get; }
    ToolCategory Category { get; }   // Validation / Build / Codegen / Utility
    string Title { get; }
    void Run(ToolContext ctx);
}

// 校验规则：Severity 与可修复性是校验独有，故独立于 IToolEntry
public interface IValidationRule
{
    string Id { get; }               // 稳定 ID，CI 与报告引用
    RuleSeverity Severity { get; }   // Info / Warning / Error
    bool Check(ValidationContext ctx);
}

// 修复是可选能力，单独的接口而非基类钩子——不可自动修复的规则不实现它
public interface IFixableRule
{
    void Fix(ValidationContext ctx);
}
```

- **发现机制**：`TypeCache.GetTypesDerivedFrom<T>()` 显式发现，不做运行时反射扫描；
- **ToolRegistry 是唯一注册源**：菜单、工具中心、批处理全部从注册表生成，新增工具零改基建（开闭原则的直接兑现）；
- **执行同源**：每个工具的本质是一个可 headless 执行的静态方法，窗口与菜单只是它的两个皮。

### 工具中心窗口（已定）

- **要集中的工具中心**：四类工具将随模块建设持续增长，集中入口降低发现成本。工具中心是唯一的框架工具窗口，两个区域——分类工具目录 + 校验报告（上次运行结果、可点击跳转资产、带修复按钮）。
- **窗口是发现层与报告层，不是执行层**：所有执行最终走同一静态方法，批处理路径不依赖窗口存在。
- 编辑器窗口用 UIElements（2022.3 编辑器窗口的标准形态），与调试平台呈现层选型同源。

### 批处理入口

`BatchEntry` 为每个工具与全量校验提供 `-executeMethod` 静态入口：CI 以 batchmode 调用，Error 级失败 → 非零退出码 → 流水线阻断。输出同时含人读摘要与机器可读清单（按工具 Id 与规则 Id 索引）。

## 校验运行策略（已定）

- **CI 阻断**：CI 全量跑 ValidationRunner，任何 Error 级失败即非零退出码；Warning 级仅报告不阻断。
- **编辑器手动**：工具中心或菜单触发，报告窗口查看，可逐条或批量执行 `IFixableRule` 修复。
- **否决构建前钩子**：`IPreprocessBuildWithReport` 时机不可靠（可被跳过、时序不受控），且把全量校验混入本地构建会拖慢每次迭代。阻断只发生在 CI 单点——本地快、远端严。

## 模块骨架脚手架（已定进第一批）

- 输入模块名，生成标准六件套（Contracts / Runtime / Testing / Content / Tests / Editor）+ 全套 asmdef（模块、Contracts、Testing、Tests、Editor），引用矩阵按 [../项目说明/架构说明.md](../项目说明/架构说明.md) 的分层规则生成。
- **脚手架是骨架规范的唯一执行者**：手建模块视为违规——规范变更时改一处（脚手架），新模块天然合规。
- 生成前做命名陷阱预检：模块名与知名类型同名（如 `Debug`、`UniTask`、`Editor`）时拒绝生成并说明。
- 产物全部是文本文件与目录（`.cs` / `.asmdef`），直接落盘后由 Unity 刷新生成 `.meta`——不触碰序列化资源，符合 UNITY-GUIDE 的直改边界。

## 工具分类

| 分类 | 解决什么 | 典型工具 | 首个消费方 |
| --- | --- | --- | --- |
| 校验与审计 | 规范从文档变成可执行检查 | asmdef 依赖方向、命名 / 目录规范、导入设置（纹理压缩、精灵设置）、引用完整性（丢失引用、重复 GUID、被引用却不进包）、Luban 配置交叉校验 | 依赖方向校验第一批；配置校验随 Luban 表落地 |
| 构建与发布 | 产出可复现、可对比 | HybridCLR 生成 / 补充元数据、YooAsset 收集规则编辑与打包、构建报告与版本差异 | 热更通道落地时 |
| 代码生成 | 一次写对，消灭手抄 | 模块骨架脚手架、协议代码（随 Shared/Protocol） | 脚手架第一批 |
| 编辑器效率 | 高频操作窗口化 | 资源引用图浏览、批量重命名等 Utility 类动作 | 随需沉淀 |

运行态辅助（命令台、作弊入口、性能表）是刻意的排除项，归调试平台 P2。

## 分期路线

| 期 | 内容 | 依赖 |
| --- | --- | --- |
| 第一批 | ToolRegistry + ValidationRunner + BatchEntry + 工具中心窗口；asmdef 依赖方向校验；模块骨架脚手架 | 无，基建与两工具立即可用 |
| 第二批 | Luban 配置交叉校验、YooAsset 收集与引用检查、导入设置审计 | 资源 / 配置模块落地 |
| 第三批 | HybridCLR 构建管线、构建报告与差异对比、CI 工作流搭建 | 热更通道落地 |

第一批交付即含可被 CI 消费的入口；CI 工作流本身的搭建（仓库基建）排在第三批。

## 已知限制（如实记录）

- 本设计未动工，以上均为规划；首块代码落地时回写本节与进度表。
- 架构规则将同时体现在三处——架构说明（文字）、脚手架（生成）、依赖方向校验（检查），三者需同步演进，这是引入工具化后的新增维护点。
- 批处理模式下工具中心窗口不可用，CI 路径只走 BatchEntry 出口，两条路径的覆盖面差异以「执行同源」原则收敛。
- CI 基础设施尚未搭建；`IFixableRule` 只承诺确定性修复，不可自动修复的问题仅报告。

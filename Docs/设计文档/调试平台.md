# 调试平台设计

`Modules/Debugging`，程序集 `WindFrameWork.Modules.Debugging`，命名空间 `WindFrameWork.Modules.Debugging`。本文仅描述当前最新设计；当前状态为规划中，代码未动工，进度见 [../施工记录/进度.md](../施工记录/进度.md)。

## 目标与边界

面向开发期的机内可观测层：聚合并呈现日志、池 / 任务 / 模块状态与性能指标，并提供一条调试命令通道。随装配清单进入开发构建，发布清单中直接缺席。

**不做**的事与做什么同等重要：

- 不替代 Profiler：性能分析仍归 Unity Profiler 与性能工程；
- 不做线上遥测：发布态的数据面、采样与隐私约束和开发期完全不同，不共用通道；
- 不干预模块生命周期：与 UniTask 桥接同一哲学，只观测不接管初始化；
- 不依赖将来 UI 模块（理由见「呈现层」）。

## 程序集与命名

按模块标准骨架自包含（Contracts / Runtime / Testing / Content / Tests / Editor），引用 Core 与其他模块的 Contracts，不引任何模块 Runtime；被观测方对本模块零感知。

**目录名取 `Debugging` 而非 `Debug`**：命名空间若以 `…Modules.Debug` 结尾，程序集内裸记号 `Debug` 会解析到命名空间而非 `UnityEngine.Debug`，而调试代码恰是全仓 `Debug.Log` 密度最高的地方。与 ObjectPool、UniTaskBridge 记录在案的「命名空间与类型同名邻接」陷阱同源。

呈现用 UIElements 随 Unity 2022.3 内置，**不新增包依赖**。

## 三面架构：采集 / 呈现 / 执行

诊断数据的所有权留在产生它的模块，本模块不定义集中式诊断数据模型（契约归属规则：接口随功能模块存放）。采集面今天大半已存在：

| 数据源 | 入口 | 状态 |
| --- | --- | --- |
| 对象池统计 | `ObjectPoolRegistry` → `ObjectPoolStatistics` | 已落地 |
| 引用池统计 | `ReferencePoolRegistry` / `ReferencePools` → `ReferencePoolStatistics` | 已落地 |
| 异步运行时 | `UniTaskBridge.CaptureSnapshot()` | 已落地 |
| 日志 | `Application.logMessageReceived` | 引擎自带 |
| 模块生命周期 | `IModule` 状态 | 随 ModuleSystem 落地 |
| 事件流量 | EventCenter 计数 | 随事件中心落地 |

呈现面按「面板」组织，契约只有一条：

```csharp
public interface IDebugPanel
{
    string Title { get; }
    // 懒构建：首次可见时创建；关闭期间零开销
    VisualElement Root { get; }
}
```

模块在自注册阶段实现并挂载面板，与 `XxxModule` 自注册的既有模式同构；统一样式经本模块提供的共享 USS class 获得，而非包装出一层 `IDebugUI`——UIToolkit 本身即抽象，再包一层属投机性抽象，出现第二个同构消费方前不落地。

热更侧同样可注册面板：热更程序集引用 AOT 契约是允许的依赖方向，对接 HybridCLR 后热更模块的业务状态观测是刚需。

执行面（命令台）对接 `Core/CommandSystem`：调试命令即普通命令，注册、调度、审计能力与业务命令同源，不另造分发器。

## 呈现层：UIToolkit 自建（已定）

- **自建而非复用将来 UI 模块**：UI 模块是业务表现层，会被热更侧定制；调试工具必须在任何构建形态下可用，反向依赖会成环。
- **选 UIToolkit 而非 IMGUI**：编辑器与运行时同一套控件与样式体系，IMGUI 属维护态。代价是叠加区需挂 `UIDocument` + 独立 `PanelSettings`（模块 `Content/` 自带，`Sorting Order` 置顶避免被业务 UI 遮挡），运行时主题资产同放 `Content/`。
- **输入**：走 EventSystem；工程启用 Input System，需配 `InputSystemUIInputModule`，调试面板聚焦时的焦点环与业务输入隔离待真机验证（见已知限制）。

## 激活与裁剪

三道门，由软到硬：

1. **装配清单**：调试模块是否进入 Bootstrap 装配清单。发布构建清单直接不含，IL2CPP 裁剪带走残余——模块系统「由装配清单驱动、可裁剪」的兑现；
2. **编译约束**：远程通道等重资产加 `UNITY_EDITOR || DEVELOPMENT_BUILD` define 约束；
3. **运行时开关**：机内呼出（悬浮球 / 多指手势），关闭时 Overlay 不更新、采样器不跑。

关态要求零痕迹：模块不在清单时业务代码无任何感知，以构建对比测试锁住。

## 性能纪律

观测工具不得拖慢被观测对象，标准与业务模块一致并配 Performance 测试：

- 统计按固定间隔采样（约 0.5s），不做每帧字符串拼接；面板仅可见时构建；
- 采样缓冲复用——`ReferencePool` 的教科书场景，自家狗粮自家吃；
- 日志捕获走线程安全队列：`logMessageReceived` 可能在非主线程回调，入队、主线程排空。

## 分期路线

| 期 | 内容 | 依赖 |
| --- | --- | --- |
| P1 | 日志台（捕获 / 过滤 / 复制）、环境信息、FPS / 内存 / GC 表、池统计面板、UniTask 快照面板 | 无，数据源已就绪 |
| P2 | 命令台（调试命令 + 作弊入口）、模块生命周期检查器、事件流量面板 | CommandSystem、ModuleSystem、EventCenter |
| P3 | 远程调试（Editor 连真机）、时间缩放 / 配置覆写、网络流量面板 | Network 模块、真机构建管线 |

远程通道单独成程序集 `Modules/Debugging.Remote/`：三块中唯一有体积与攻击面的，独立后 P1 / P2 在受限构建中依然完整——与「DI 变体独立成程序集」同一手法。

## 已知限制（如实记录）

- 本设计未动工，以上均为规划；首块代码落地时回写本节与进度表。
- UIToolkit 运行时在 IL2CPP + 裁剪下的包体增量未实测，首个开发构建时量化。
- 调试面板与业务 UI 的焦点 / 输入冲突需真机验证，尤其 Input System 下的事件路由。
- 命令台随 CommandSystem 排期，P1 不含执行面。
- 服务端监控不在此范围：按架构规则走 .NET 原生生态，不从客户端移植。
